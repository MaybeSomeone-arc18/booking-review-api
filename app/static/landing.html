The lifecycle

One booking, four states, three roles. Every transition is enforced server-side.

Book

A customer creates a booking against a provider's slot. Creates are rate-limited in Redis.

Confirm

The provider confirms - or the customer cancels while it's still pending.

Complete

The provider marks the job done. Only completed bookings can be reviewed.

Review

The customer leaves a 1-5 rating and text. One review per booking, enforced by the database.

Under the hood

A queue worker keeps the request path fast: summaries are jobs, not requests.

Browservanilla JS SPA, zero build step -> FastAPIJWT auth, role-based access -> PostgreSQLusers, bookings, reviews -> Rediscache, rate limits, job queue -> Workerwrites review summaries back

Built to be audited

The interesting engineering is in what the API refuses to do.

Cross-tenant reads return 404, not 403 - no existence leaks between users.
Reviews only attach to completed bookings; anything earlier is rejected.
Duplicate reviews hit a Postgres uniqueness constraint and come back 409.
20+ booking creates in a minute trip a Redis rate limiter: 429.
Every role sees only its own surface - customer, provider, and admin queries differ by design.
Schema is Alembic-managed; the test suite runs migrations against real Postgres in CI.
