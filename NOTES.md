# Design decisions and known gaps

**Schema decisions.** Three tables: users, bookings, reviews. Users carry a unique case-insensitive email, a bcrypt password hash, and a role enum (customer, provider, admin). Bookings reference customer_id and provider_id as foreign keys into users, store start/end timestamps, and a status enum that moves pending -> confirmed -> completed, or cancelled. Reviews reference booking_id with a uniqueness constraint, so the one-review-per-booking rule is enforced by the database itself, not just application code - a duplicate attempt comes back as 409 from the constraint rather than a race condition. Ratings are constrained to 1-5 at both the Pydantic schema and the database level. Migrations are Alembic-managed, run automatically at container start, and CI applies them against a real Postgres service before running tests.

**RBAC approach.** Stateless JWT auth (HS256 with expiry), role embedded in the token. FastAPI dependencies resolve the current user and enforce per-route role rules: customers create bookings and reviews, providers confirm and complete bookings and request review summaries, admins read everything. Cross-tenant reads deliberately return 404 instead of 403, so one user cannot probe whether another user's booking even exists. Status transitions are validated server-side: a provider cannot complete a booking that was never confirmed, and only completed bookings accept reviews. The demo UI mirrors the three roles, but every authorization decision lives in the API.

**Production-readiness gaps, honestly.** (1) Password handling is minimal: no strength policy, no reset flow, no email verification. (2) JWTs are not revocable; a stolen token stays valid until expiry, so a refresh-token or denylist design would be next. (3) The rate limiter is a fixed 20-creates-per-minute Redis counter - fine for the demo, but production would want per-endpoint sliding windows and identity-aware limits. (4) The summary worker runs in-process to fit the free-tier deployment; production would split it into its own service with retries, dead-letter handling, and structured logs. (5) No audit log for admin reads, no hardened pagination, and secrets are plain environment variables rather than a managed vault. (6) The frontend is a zero-build static SPA by design: it demonstrates every API surface, but it is not a production client.

**Deployment.** docker compose up reproduces the whole stack (api, postgres, redis, worker). A live instance runs on Render with GitHub Actions CI (ruff, pytest, real Postgres migrations) and scheduled keep-warm pings.
